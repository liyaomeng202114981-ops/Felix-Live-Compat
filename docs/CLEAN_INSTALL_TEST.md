# 从零安装验收

## RC3.3 窗口采集中缩小伴侣丢画面

2026-11-20 用户指出窗口采集中缩小伴侣后画面消失，要求直接查看屏幕。原 Dock 版使用自有 `Felix Resize Capture Test` 自动复现，明确区分两条故障链：

1. Python `window_surface_state.py` 在窗口隐藏或尺寸变化后继续 `XGetImage`，未捕获的 `BadMatch` 使维护程序退出，启动器随后结束兼容会话。
2. 修正第一项后，主界面仍在，但媒体子进程退出。服务日志记录 Xlib 原生 `BadMatch`，请求号 73（`X_GetImage`）；Media SDK 同时记录崩溃，随后 IPC 连续超时。DMA-BUF 两秒 ACK 超时关流发生在后面，属于结果。只保留租借并延长等待的试验没有恢复预览，已撤回，最终包保留原有的有界等待。

### 修正与源码对应

- [表面维护](../src/wgc-compat/window_surface_state.py)：未映射时跳过像素读取；映射状态与读取之间的 X11 瞬时异常由下一事件／兜底检查重试。
- [0074 原生补丁](../patches/wine/0074-winex11-Tolerate-overlay-readback-resize-races.patch)：透明输入形状维护已有 XShm 错误保护，但其 `XGetImage` 回退没有。仅在该读取请求范围捕获 `BadMatch`、`BadDrawable`、`BadWindow`，保留当前输入形状，后续 present 重试。其他 X11 错误继续原路径，不修改采集内容或编码。
- [构建清单](../tools/wine_runtime.py) 从锁定源码依序应用 0066–0074。GPU UI、DMA-BUF、声音、直连及 UnityCapture 回退配置保持。
- [隔离回归](../src/wgc-compat/test_window_surface_state.py) 覆盖隐藏主窗跳过采样、读取竞态和后续输入范围恢复，在独立 Xvfb 通过两项测试。固定 SDK 的 Wine Werror 构建通过。

### 现场验证

原生组件在伴侣退出后安装，再从同一入口重开。八轮连续缩放共 336 次宽度变化，保留同一服务会话、媒体进程和窗口 socket。每轮直接检查伴侣像素，均有有效红／绿测试画面；结束后六次时间采样同时读到红色和绿色，截图帧号继续增长。另做八次宽高组合变化，媒体进程持续存活；按 GNOME 当前绑定的 Super+H 实际最小化（WM_STATE=Iconic、HIDDEN），从同一窗口恢复后再次采到红／绿变化。验证仅针对自有窗口与本轮缩放故障；未开播，未重做用户已取消的整套共享／音频测试。

### 回退

关闭兼容版后使用此前保留的 RC3.1 包恢复 `winex11.so` 和 `window_surface_state.py`。账号前缀、声音和网络配置无需替换。RC3.2 是只含 Python 保护的中间包，未解决第二项，不作为该故障的通过版本。RC3.3 本地补充包尚未再次进行空前缀安装；此前 RC3 从零安装的结论不等同于本轮新包从零验收。

```bash
xvfb-run -a /usr/bin/python3 -B src/wgc-compat/test_window_surface_state.py
```

## RC3 从零重装与后续 UI 修正

2026-11-20 将现有安装和入口完整备份，再用 RC3 原包及官方 Windows 安装器在同一路径创建全新前缀。五个 Wine 模块、安装后的 UI 脚本和原图标均与包内文件一致。用户扫码进入，确认启动时有短暂停顿。后续指出放大时偶尔露出后方桌面，此现象有别于此前整块白屏。

默认透明背景的扩大过程采到 3 个透明样本。给主窗新区域预设不透明深色背景后，本轮 175 个样本均未采到透明点，用户反馈明显改善并决定先保留。该背景设置整理为 RC3.1 的 UI 补充，启动时随维护程序应用。RC3 原包保留，RC3.1 未另做一次空前缀安装。

用户随后取消本轮重复共享与音画录制测试。日志中已有实际显示器和窗口授权及有效帧，但此次不追加完整媒体回归通过结论。自有测试窗已清理，当前单一安装继续保留。

## RC3 白帧与点击延迟

RC2 的定时扫描遍历 182 个根窗口，一次两秒样本约占单核 CPU 的 24%。RC3 监听窗口结构、属性及 Shape 事件，只检查已登记的应用窗口，另有两秒低频兜底。对应样本中维护程序空闲 CPU 约 0.5%，四次自动缩放未采到输入范围落后。这个短样本用于定位维护开销。

高频采样还观察到辅助窗在缩放时短暂变成完整可见区域，同时 Wine 删除了零 opacity 属性。只从外部补回透明度仍会出现白帧。0073 补丁在驱动同步窗口透明度时处理该角色，须显式开启 `WINE_X11_INVISIBLE_DECORATION=1`、命中已有的精确类名 profile，且为同进程 captioned owner 的大型 layered／transparent 无边框辅助窗。主窗与小弹窗走原路径。维护程序对已经验证的装饰角色跨缩放保持隐藏，角色改变或进程退出时恢复临时属性。

固定 SDK 的 Werror 构建通过。退出伴侣后安装新的 `winex11.so`，保持 GPU 界面渲染。六次缩放共 43012 次辅助窗属性采样均为零 opacity。用户随后多次最大化、还原和标题栏下拖，确认白帧消失，点击和拖动正常。隔离 X11 验证覆盖输入范围修正、其他 PID 与可见窗口拒绝、装饰角色跨缩放维持及退出恢复。此次用户要求先专注 UI，RC3 的共享与录制回归暂缓。

## RC2 窗口表面修正

2026-11-20 的最终重装暴露出 RC1 最大化白屏和输入范围过期。窗口从 1280×720 放大到 1920×1051 后，主窗输入范围仍停在旧尺寸。完全不可见的直属辅助窗还可能保留全屏标记及整窗输入。一次白屏复现时主窗原始图像完整，因此这些现象涉及呈现和输入状态同步。

修复先核对 PID、WM_CLASS 和直属 owner。对不透明主窗的过期输入尺寸恢复默认范围，仅对 Bounding 完全不可见的 32 位直属大辅助窗维护零 opacity 和空输入。辅助窗重新可见或维护程序退出时恢复临时属性。程序跟随伴侣的独立服务退出。

关闭 Chromium GPU 的初次对照与表面维护的测试时段重叠，不能单独归因。随后恢复原 GPU 渲染，仅保留表面维护，用户确认两轮最大化、按钮还原和标题栏下拖全部正常。隔离测试覆盖可见窗口及其他进程拒绝、输入尺寸恢复、辅助窗重新可见和原 opacity 恢复。

## IPC 缺失的复现与修正

官方下载版和日常版的客户端构建号均为 `13.3.5.564315535`。两套安装的 414 个共同 Windows 应用二进制逐字节一致，DXVK 基础库和 Vulkan 桥也相同。新前缀移入匹配的采集模块及 XWayland 驱动后仍停在 `no sdk`。清除透明辅助窗的输入区域以及把显示器授权提前到启动前，均未让 SDK 进入就绪。授权后的 PipeWire 流持续产生有效帧，租借数仍为 0。

在同一隔离前缀保持应用内共享模式，只补装 Wine `FileReplaceCompletionInformation` 实现对应的 `ntdll.so`、`wow64.dll` 和 `wineserver`。Media SDK 从 `ready` 到 `restarting`，再回到 `ready`。候选全屏获得 1920×1080 动态桌面，GPU 租借继续增长。随后从空场景添加独立 Wayland 测试窗口，收到 828×479 的动态画面，使用显式同步，用户核对变色和递增帧号。本地录像解码验证了动态测试画面和完整的 8 秒 880 Hz 测试音，文件为 1280×720、30 fps HEVC 视频和 48 kHz 双声道 AAC 音轨。

原构建只打包了 Wayland／WGC 侧，通用运行器还缺少该 IPC 实现。新构建从固定 Wine 源码生成配套客户端与服务端模块，并在初始化新前缀前成套安装。另一项独立对照确认，使用不同 NVENC 环境的辅助命令会让 Proton 移除同一前缀的 NVIDIA 编解码 DLL。工具统一了这个前缀的安装、注册、主进程和辅助进程的相关启动参数。
