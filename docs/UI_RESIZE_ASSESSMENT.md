# 窗口缩放性能：当前结论与实验边界

记录日期：2026-11-20。本文件归档 RC3.4 之后的独立实验，未将实验配置部署为发行默认。官方客户端 `13.3.5.564315535`，Chrome 引擎报告 `136.0.7103.59`，RTX 4060／NVIDIA 615.71.09，GNOME Wayland／Wine XWayland，当前显示器约 239.66 Hz。测试保持音画、网络和系统显示配置。

## 卡在哪里

对自有空场景执行 40 Hz 尺寸请求，跟踪 Chromium 布局、绘制、提交与输出阶段。单次阶段中位数如下：

| 阶段 | 默认 ms | 独立 ANGLE Vulkan ms |
| --- | ---: | ---: |
| Layout | 0.103 | 0.116 |
| Paint | 0.023 | 0.024 |
| Commit | 0.082 | 0.100 |
| GPU 线程输出表面 Reshape | 11.285 | 0.432 |
| 浏览器同步缩放等待 | 19.120 | 0.189 |
| SwapBuffers | 9.314 | 1.037 |

默认同步等待占该 3.4 秒测量窗口约 2.512 秒。各线程阶段会重叠，不能相加为整帧耗时，也不能将 CPU 线程跨度称为 GPU 硬件执行时间。当前证据优先指向表面重建与呈现同步，不能单凭 Wine 存在就将所有卡顿归因于它。

## 不带跟踪的对照

统一预热，按默认 A1 → Vulkan B → 默认 A2，每组 3×68 次、10 Hz 尺寸请求。测量关闭图标在新位置重现的客户端图像代理：

| 配置 | 样本数 | 中位 ms | 成功样本 p95 ms | 100 ms 内未检出 | 进程组 CPU，单核=100% |
| --- | ---: | ---: | ---: | ---: | ---: |
| 默认 A1 | 204 | 61.08 | 94.18 | 25 | 378.76% |
| Vulkan B | 204 | 43.76 | 72.89 | 2 | 355.33% |
| 默认 A2 | 204 | 61.58 | 95.41 | 25 | 373.67% |

612 次中，该代理中位数约改善 29%，但不是鼠标到物理显示器延迟、完整帧率或观众端质量。p95 只含成功样本，必须同时看未检出数。像素读取会影响测量，宿主仍有其他应用运行。另一个不读像素的 40 Hz 条件中，Vulkan CPU 约 443%，默认约 182–187%；不能宣称总负载降低或无性能损失。

Vulkan 条件保留硬件合成及 WebGL，但 GPU 光栅化报告未启用。候选普通入口与 27 个图像／输入样本通过，不代表所有过渡逐帧检查，也没有重新验证共享、录制、音轨和开播。因此发行 RC3.4 保持原后端。

## 接口与原生 Linux 客户端

独立 0075 只为缺失 D3DKMT 优先级入口提供非致命的不支持返回，不调整 Linux GPU 调度。实际查询来自 Media SDK；原对照也能启用硬件 UI。它没有可靠缩放收益，不放入本发行。

星火版 `com.douyin.otohime 8.7.1` 是 Linux ELF／Electron 加载抖音网页。运行中 renderer 走 Wayland，并带 `--disable-gpu-compositing`；不是 Windows 伴侣的同产品对照，不能定量分离 Wine 开销。原生 Linux 窗口路径值得研究，但抖音伴侣安装中存在 Windows PE 原生插件，不能仅替换 Electron。见[路线一规划](NATIVE_UI_ROUTE_ONE.md)。

Windows 原生与 Wine 的严谨对照应使用同一客户端构建、同一硬件、显示刷新率、缩放比例和空场景；分别比较两边默认／ANGLE Vulkan。macOS 或星火版仅作体验参考。本轮没有原生 Windows 实测。

## 黑盒复测与受控开关（2026-11-21）

为把上面的追踪结论变成可重复的外部测量，另建了一个不接触客户端代码的黑盒基准：用 XGetImage 读客户端自身 drawable 的像素，用 `configure` 请求改变窗口尺寸，用 cgroup 读客户端 CPU。每个目标尺寸先在同尺寸下校准稳定参考帧（连续两帧一致才接受，闪烁或视频补丁按尺寸屏蔽），再按 10 Hz 固定节拍发 68 次尺寸请求（1280x720 → 1455x797），比较"画面真正变成该尺寸应有样子"的时刻；未匹配的步单独计数并计入 100 ms 以上的统计。测试期间窗口被置顶，遮挡检测基于系统截图逐点比对，遮挡比例 >15% 时复测一次。

同一安装、同一客户端、同一代理点、交替启动的对照结果：

| 配置 | 轮次 | 匹配样本中位 ms | 100 ms 内未取证比例 | 客户端 CPU（单核=100%） |
| --- | ---: | ---: | ---: | ---: |
| 默认后端 | 4 | 7.9 – 60.5（同配置跨轮波动大） | 22 – 37% | 277 – 385% |
| ANGLE Vulkan | 5 | 22.6 – 29.5（稳定） | 7 – 29% | 222 – 303% |

黑盒数据比上面的追踪数据噪声大，不能用来宣称 19 ms 级同步等待已完全消除；可重复的部分是：Vulkan 条件下"内容追帧"中位稳定落在二三十毫秒，且客户端 CPU 明显低于默认后端（闭环节拍下约 222–224% 对 349–355%）；默认后端在同条件下中位与未取证比例波动更大。这与内部追踪（同步缩放等待 19.120 → 0.189 ms、输出表面 Reshape 11.285 → 0.432 ms）以及 612 样本代理对照（中位 61.08 → 43.76 ms、100 ms 内未检出 25 → 2）方向一致。

同日给启动器加了受控开关，默认值不变、发行默认仍是已完整验收的默认后端：

```bash
python3 tools/felix_live.py launch --root <安装根> --direct --ui-renderer vulkan
```

`--ui-renderer default`（缺省）即原始启动方式；切回默认只需不带参数重启。共享、录制、音轨、开播与长时稳定性没有在 Vulkan 下复验，因此不把它设为默认，也不更新发行包；需要试用或复测时用上述开关，停止后按默认启动即可回退。
