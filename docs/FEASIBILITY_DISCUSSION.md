# 路线一讨论、可行性与复杂度

记录日期：2026-11-20。用户因额度紧张决定先停止继续开发，保存现有工作；不自动安排后续任务，不切换日常安装。

## 问题与方向

用户希望 Ubuntu 直播伴侣获得接近原生的窗口缩放、最大化、拖动和操作体验，核心范围是桌面／窗口共享、声音、开播、本地录制与常用界面。摄像头等扩展功能不是当前优先项。

星火版抖音使用 Linux Electron 包装抖音网页；Windows 伴侣则同时依赖定制引擎、Windows 原生插件和媒体 SDK。不能直接用 Linux Electron 替换全部运行时。原方案的缩放跟踪主要阻塞在输出表面重建与同步等待，布局／绘制本身较短。

路线一拟保留 Windows 媒体后端，由 Linux 界面异步控制并呈现图像。目标是界面缩放时不再同步等待 Windows 媒体输出表面重建，但并不自动解决所有加载、网络、业务或媒体问题。

## 已验证与未验证

已验证两层原型：Linux 自有 UI 与独立 Linux 测试生产者的解耦；以及 Linux 界面调用独立 Wine 宿主中的官方插件，初始化真实 SDK，取得 `13.3.5.7` 版本、渲染并切换自有 320×180 场景、接收两张真实快照。静态快照 RGB 像素匹配、Linux 解码自检通过。

先前 metasecml.dll 的退出，通过沿用已安装客户端的原产品初始化配置解决。没有提供账号／设备标识，没有改模块检查或返回假成功。源码不包含厂商配置值。独立运行器含此前 0075 实验，各组保持；未新增原 RC3.4 GDI32 对照。

尚未实现持续视频帧、GPU 零拷贝、原前端迁移和完整音画链路，也没有测得完整客户端的原生体验改善。小型 demo 较顺滑不能作为同负载性能证明。

## 工作复杂度评估

| 工作 | 复杂度 | 当前边界 |
| --- | --- | --- |
| 基本控制与独立 SDK | 中等 | 初始化、查询及静态快照已通，其他能力待验证 |
| 持续帧、时间轴、关闭清理 | 高 | 快照文件传递需要替换为有界的持续通道 |
| GPU 共享与显式同步 | 很高 | Linux 不能直接使用 Windows 纹理句柄，尚未验证预览方向零拷贝 |
| 原前端与 Windows 插件适配 | 高且不确定 | 14 个原生插件文件及定制引擎依赖需要梳理；不能仅按页面数估计 |
| 登录、窗口、托盘、快捷键、退出及恢复 | 中高 | 原生架构下需逐项接入、验证和处理异常 |
| 随 Windows 客户端更新 | 持续维护 | 私有协议、模块编号、ABI 及前端变化可能要求重新适配 |

完整核心需求属于中大型移植工作。能复用原前端并替换少量平台接口时，工作量较可控；若大量私有业务需要重写，成本会显著扩大。当前没有足够依据承诺完整工期、全部功能兼容或与 macOS 完全相同的表现。

## 恢复工作时的顺序

1. 将真实 SDK 快照通道扩展为持续帧流，测试缩放中更新、暂停／恢复、退出和有界队列。
2. 量化 CPU 拷贝与 GPU 传递的成本，再验证共享纹理／DMA-BUF 格式和同步；不把现有采集方向的成果当作预览方向已通过。
3. 用相同素材做本地音画录制闭环，原型仍不自动开播。
4. 梳理原前端和本地插件调用边界，决定可复用范围，再扩大到常用 UI。
5. 补独立安装、异常恢复和跟版验证，通过后才讨论日常切换及完整发行。

本轮已保存原型与证据，不在额度紧张时继续扩大实现。实际运行与回退见[实验 README](../experiments/wine-sdk-bridge/README.md)，详细阶段与预期效果见[路线一规划](NATIVE_UI_ROUTE_ONE.md)。
